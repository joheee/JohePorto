# johePorto: Core Context

Personal portfolio site. Next.js (App Router, TypeScript, Tailwind) on Vercel, Firebase (Firestore + Auth) as the backend.
All public content (name, hero, bio, skills, experience, education, projects) lives in Firestore and is edited from a private admin. The same data generates an ATS-friendly resume PDF.

- **Live:** https://www.johe.my.id (custom domain; the apex `johe.my.id` redirects to `www`, and `johedotcom.vercel.app` still works and canonicalises to `www`). Vercel project `johedotcom`.
- **Firebase project:** `joheportobackend` (one project shared by local dev and production: same data, same rules)
- **Repo:** github.com/joheee/JohePorto, branch `main`
- **Read first:** `AGENTS.md`. This is Next.js 16: APIs differ from older versions. Read the relevant guide in `node_modules/next/dist/docs/` before writing code.

## Firestore data model

**`settings/profile`** (single document, the whole public profile)
`name`, `roles[]` (rotating hero line), `pitch`, `email`, `location`, `status`, `focus` ("Now" tile), `bio[]` (paragraphs), `skillGroups[{name, items[{name, aliases[]}]}]` (the skill catalog, edited in Settings > Skills) with a derived flat `skills[]` (names only, never edited; a profile that only has legacy `skills` shows them as one group "Skills"), `socials[{label,href}]`, `experience[]`, `education[]`, `reviews[]` (added 2026-10-05, see "Step 9"), `updatedAt`.
Each `experience` item: `role`, `company`, `summary` (lines starting with `•` or `-` render as bullets), `location` (optional, shown after the company; older entries have none), `stack[]` (technologies, shown as chips under the entry; older entries have none), `current` (bool), `startMonth`, `startYear`, `endMonth|null`, `endYear|null`, `createdAt` (Firestore **Timestamp**, kept on edit, stamped when an entry is first saved). Sorted on the site LinkedIn-style: current roles first, then by end date, then start date. Experience is a free-order array in the admin; sorting is display-only.
Each `reviews` item: `name`, `role` (optional), `text` (the quote), `link` (optional https URL where it can be checked); older profiles without the field load as `[]`. Each `education` item: `school`, `degree`, `location` (optional), `summary` (same bullet formatting, e.g. GPA), `current`, start/end month+year like experience. Shown on the site as a second timeline under Experience (newest first, same sorter); edited in Settings > Education. Older profiles without the field load as `[]`.
Skills catalog rules (`lib/skills.ts`, pure): names match on a normalised key (lowercase, letters/digits/`+`/`#` only), so React JS = ReactJS = react.js; real synonyms use `aliases` (Go / Golang). A spelling can belong to one skill only (validated). Job and project `stack` chips suggest catalog skills while typing (`ChipsInput` `suggest`/`resolve`). Settings > Skills shows a tray of stack names not in any group (add one by one or all at once) and spelling variants. **Saving the profile rewrites every job stack and every project stack to the catalog spelling** (project `updatedAt` untouched); `saveProject` does the same for that project. Group order is the array order (Settings > Skills has Up/Down buttons per group, keyboard- and screen-reader-friendly); it drives the public tile and the resume. The public About tile shows the groups (no heading when there is only one group).
Fallback: if the document is missing/invalid the site shows placeholder content from `src/lib/content.ts` (`defaultProfile`).

**`projects/{slug}`** (document ID = slug, immutable)
`title`, `summary`, `description` (same bullet formatting), `stack[]`, `links[{label,href}]` (**at least one required when saving**; older projects with none still load and show one blank row to fill in), **`month`, `year`** (manual "Created" date, required), `updatedAt`.
Shown **oldest first** by month/year, ties by title. No `order` field any more.
Legacy: a project saved before month/year existed (currently `postgresql-physical-backup-with-pgbackrest`, still has `order: 0`) falls back **at read time** to the month it was last saved (shows "Oct 2026"). Edit it in `/admin/projects` to set the real date.

**`messages/{id}`**: `name`, `email`, `text`, `read` (bool; missing = unread), `createdAt` (Timestamp). Written by the API route only.

**`analytics_days/{yyyy-mm-dd}`**: counters only (views, visitors, bots, maps country/device/browser/lang/theme/ref/utm/sections/events) plus a `day` field; written by `/api/collect` through the Admin SDK. **`analytics_seen/{day}_{hash}`**: the one-day visitor hash, deleted after 2 days. Both are private (not in `firestore.rules`, so denied to clients). Full description in the Analytics entry.

**`posts/{slug}`** (document ID = slug, immutable; `new` is reserved): `title` (120), `excerpt` (200, required), `content` (Markdown, 60000), `tags[]` (8 x 30, lower case, spaces become hyphens), `status` (`draft`|`published`), `publishedAt` (Timestamp, set the first time it is published and kept after that, `null` while never published), `updatedAt`. Written by `savePost` (Admin SDK); rules already existed. Types `Post`/`PostSummary` in `types/content.ts`, `parsePost` in `lib/validation.ts`.

### Security rules (`firestore.rules`, must be published in the console by hand)
Owner = a single hard-coded UID. Public read: published posts, projects, settings. Public create-only on `messages` (field/size limits). Everything else owner-only. **The app itself uses the Admin SDK (bypasses rules)**, so rules protect against direct client access with the public web config.

## Architecture

**Reading data:** server components call `getProfile()` (`lib/settings.ts`), `getProjects()`/`getProject()` (`lib/projects.ts`), `getMessages()` (`lib/messages.ts`): Admin SDK, `server-only`, wrapped in React `cache`; `getProfile()` and `getProjects()` additionally cache the Firestore read across requests with `unstable_cache` (tag `site`, see Caching). Firestore Timestamps are converted to ISO strings before reaching client components.

**Writing data:** Server Actions in `src/app/admin/(protected)/actions.ts` (`saveProfile` (also rewrites job and project stacks to the catalog spelling), `saveProject`, `deleteProject`, `setMessageRead`, `deleteMessage`). Every action: re-checks the owner (`getAdmin()`), validates with `lib/validation.ts` (`parseProfile`, `parseProject`; server is the source of truth, forms also use native `required`), writes with the Admin SDK, then invalidates. Profile/project actions call `updateTag("site")` (clears the cached reads, read-your-writes) and `revalidatePath("/", "layout")` (rebuilds the static PDF/metadata routes); message actions only revalidate `/admin/messages` + `/admin`.

**Auth:** the login form posts the email and password to `POST /api/login` (changed 2026-10-06, see "Rate limits"). The server checks them against Firebase Authentication through its REST API (`lib/firebase-rest.ts`, `accounts:signInWithPassword`, the web API key `NEXT_PUBLIC_FIREBASE_API_KEY` plus a `Referer` of the site so a referrer-restricted browser key still works), then verifies the returned ID token (revocation check, UID === `ADMIN_UID`) and sets an httpOnly session cookie (`lib/admin-session.ts`) that is valid for **3 hours from sign-in** (`SESSION_MAX_AGE_MS` in `lib/session-cookie.ts`; absolute, not extended by activity; Firebase signs the expiry into the cookie so the server enforces it). After that, admin pages redirect to `/admin/login` and a save returns "Not authorized. Please sign in again." (unsaved form edits are lost, so save before a long break). Cookies issued before a change keep their old expiry: sign out, or call `adminAuth().revokeRefreshTokens(uid)`, to cut them off. `lib/auth.ts`: `getAdmin()` / `requireAdmin()` verify the cookie on **every admin page and action** (layouts do not re-render on client navigation). `src/proxy.ts` (Next 16's middleware) is only an optimistic redirect for cookie-less visitors. Never rely on it alone.

**Caching:** pages render per request (CSP nonce, see Security headers); the Firestore reads are cached with `unstable_cache` (tag `site`) and cleared by `updateTag("site")` on saves. Saves made in the **production** admin therefore show immediately. Saves/writes from **local dev or scripts write to the same Firestore but cannot clear production's cache**: they show after the hourly refresh, the next deploy (the deploy id is part of the cache key) or a save in the prod admin. `/resume.pdf` is still static and rebuilt by `revalidatePath`.

**Validation limits** (see `lib/validation.ts`): name 80, pitch 300, bio 8x1500, skill groups 12 x skills 40 (name 40, aliases 8x40), roles 8x60, socials 10, experience 20 (summary 2000, role/company/location 100 single-line, stack 20x40), education 10 (school/degree/location 100, details 1000), reviews 12 (name 80, role 100, text 1500, link 500 and http(s) only), projects: title 100, summary 200, description 3000, stack 20, links 10, slug `[a-z0-9-]` max 60.

**UI system:** colour themes via `data-theme` (the id) and `data-mode` (`dark`|`light`) on `<html>`, set before paint by the inline script from `lib/themes.ts` (see "Themes"); tokens in `globals.css`; the `dark:` variant follows `data-mode`. Rule for corners: every clickable control is `rounded-lg`, only labels (chips, tags, pills that are not clickable), dots, avatars and bars are round (see "Button radius"). Shared admin pieces: `fields.tsx`, `FormCard`, `ChipsInput`, `AutoTextarea` (auto-height, also used on the public contact form), `ConfirmDialog` (native `<dialog>`, replaces `confirm()`/`alert()` everywhere), `DateSelects` (month/year), `AdminNav` (active tab), `Icons`. `SettingsForm` and `ProjectForm` share the same pattern (single `form` state, `toPayload()` doubles as the dirty check, `saved` snapshot for Discard, `beforeunload` warning). Public: `Section`, `Reveal`/`TimelineItem` (motion), `FormattedText` (bullet lines), `ProjectCard` + `ProjectChips` + `ProjectLinks` (`components/ProjectCard.tsx`: the full project card, shared by the public section and the admin list; the first link is the filled main button; `footer` slot for admin actions; `ProjectChips` is also used by the Experience timeline), `PingDot`, `CopyEmail`, `MobileMenu`.

**Env vars** (`.env.example`; real values in `.env`, gitignored; same names set in Vercel Production):
`NEXT_PUBLIC_FIREBASE_*` (6 web-config values), `FIREBASE_SERVICE_ACCOUNT_KEY` (service-account JSON, one line, **no surrounding quotes in Vercel**), `ADMIN_UID`, optional `NEXT_PUBLIC_SITE_URL` (custom domain; otherwise `VERCEL_PROJECT_PRODUCTION_URL`, else localhost). `NEXT_PUBLIC_*` are baked in at build time: redeploy after changing them. **Optional analytics variables** (also in `.env.example`): `ANALYTICS_ENABLED` (`1` counts in development too, `0` switches counting off everywhere; by default only production counts), `ANALYTICS_SALT`, `ANALYTICS_TIMEZONE` (e.g. `Asia/Jakarta`; days are counted in it, default UTC). **What `ANALYTICS_SALT` is for:** the one-day visitor hash is `sha256(salt + day + IP + user agent)`; only the hash is stored, to count a person once a day without keeping who they are. A secret salt stops anyone who got the stored hashes (they live two days in private Firestore) from reversing them by trying every IPv4 address; without it the code falls back to `ADMIN_UID`, which is weaker because the UID is written in `firestore.rules` in the public repo. It protects nothing else (not the admin login), so losing it costs nothing. **To set it:** `openssl rand -base64 32`, add `ANALYTICS_SALT` for Production in Vercel (Settings > Environment Variables), redeploy; never commit it. Changing it later is safe: people already counted that day may be counted once more (that day's visitors slightly high), no history is lost (only daily totals are kept); no need to rotate (the day is already in the hash). Recommended to set both `ANALYTICS_SALT` and `ANALYTICS_TIMEZONE` in Vercel (not done yet as far as known).

## Gotchas and decisions (learned the hard way)

**Vercel / Firebase**
- `firebase-admin` is pinned to **13.x**. v14 pulls `jwks-rsa` 4 -> ESM-only `jose` 6 loaded with `require()`, which crashed `/admin/login` on Vercel (`ERR_REQUIRE_ESM`) while working locally on Node 26. `engines.node` is 22.x; check the Vercel project's Node setting too.
- Missing `NEXT_PUBLIC_FIREBASE_*` at build time makes any page importing the client SDK 500 with `auth/invalid-api-key` (the home page does not import it, so it looked fine).
- Firestore `serverTimestamp()` cannot be used inside arrays: experience `createdAt` uses `Timestamp.fromDate`.
- Both environments share one Firestore: a schema change can break the *currently deployed* code reading the same documents. Deploy new code **before** saving data in the new format; when removing/renaming a field the old code requires, keep it until the deploy is live.
- Disable sign-ups in Firebase Auth settings (not verified done): the owner check is the UID, but open sign-up is unnecessary exposure.

**Next.js 16 / Tailwind 4**
- `middleware` is `proxy.ts`; `cookies()` is async; typed `LayoutProps<"/">` helpers (a type-check in a scratch copy fails with "Cannot find name 'LayoutProps'" until `next build`/`next dev` has generated them: not a real error); no `cacheComponents` here. Pages are now dynamic (nonce) with `unstable_cache` for data and `updateTag` in Server Actions; `revalidateTag` needs a second argument (`"max"`), `updateTag` is for Server Actions only. Static routes left: `/resume.pdf` (`force-static`), sitemap, robots, icons, OG images.
- Tailwind v4 `translate-*` uses the CSS `translate` property (not `transform`); `hover:` only applies on hover-capable devices (`@media (hover: hover)`); `transition-colors` also animates `outline-color`.

## Security headers
Plain headers live in `next.config.ts` `headers()` (all paths): `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera, microphone, geolocation, payment, usb, browsing-topics off; clipboard stays on for the copy-email button). HSTS comes from Vercel. securityheaders.com: A. Mozilla Observatory's only deduction was `'unsafe-inline'` in `script-src`, which is now **removed**.

**CSP is nonce-based** (`src/lib/csp.ts` builds it, `src/proxy.ts` sets it with a fresh nonce on every page request): `script-src 'self' 'nonce-X' 'strict-dynamic'`, `style-src 'self' 'nonce-X'`, `style-src-attr 'unsafe-inline'` (inline `style=` attributes from motion and the hero cannot take a nonce; this is the one remaining relaxation), `default-src 'self'`, `img-src 'self' data: blob:`, `font-src 'self'`, `connect-src 'self'` + `identitytoolkit.googleapis.com`, `securetoken.googleapis.com`, `www.googleapis.com` (Firebase Auth on the login form), `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'`, `upgrade-insecure-requests` (production only). Dev: `'unsafe-eval'`, `ws:`/`http://localhost:*`, and `style-src 'self' 'unsafe-inline'` (Turbopack injects un-nonced `<style>` tags). The proxy `matcher` skips `/api`, `_next/*`, `/resume.pdf` (a CSP on a PDF can stop Chrome's viewer), robots, sitemap, icons and OG images, and link prefetches. `RootLayout` is `async`, reads `x-nonce` from `headers()` and puts it on the theme `<script>`; **reading request headers there is what makes every page dynamic**. Next adds the nonce to its own scripts automatically. The JSON-LD block is not executable, so it needs none.

**Why not the alternatives:** `'unsafe-inline'` (the old policy) fails Observatory; experimental SRI + strict `script-src` was tried and **breaks the app** (Next emits ~26 inline `self.__next_f.push(...)` scripts per page that SRI cannot cover: no hydration); hashing inline scripts is impractical (their content includes page data and changes per build). Nonces were the only route.

**Cost and how it is kept cheap (shipped in `c95a48d`):** pages are no longer static/CDN-cached (`/` and the admin show as `ƒ` in the build output); only the PDF, sitemap, robots and icons stay static. To avoid a Firestore round trip per view, `getProfile()`/`getProjects()` wrap their Firestore read in `unstable_cache` (tag `site`, `revalidate: 3600`, key includes `VERCEL_GIT_COMMIT_SHA` so a deploy starts with a fresh cache). A failed read throws inside the cached function, so a failure is never cached (the outer `cache()` wrapper falls back to placeholders/`[]`). **`guard()` in `actions.ts` calls `updateTag("site")` + `revalidatePath("/", "layout")`** on profile/project saves, so a save shows on the site and rebuilds the PDF at once. Caveat (same as before): writes made outside the production app (local dev, scripts) do not clear production's cache; they show after an hour, or after the next deploy, or the next save in the production admin. Measured locally on production builds (Lighthouse, mobile/desktop): static 97/100, nonce 98/100, TTFB 3ms vs 10ms; **this excludes Vercel's function/network overhead, so expect a somewhat higher real TTFB than the old CDN-served static HTML** (re-run PageSpeed after deploying and compare with the earlier 96 mobile / 99 desktop; if it drops a lot, revert the commit to get static pages back).

Verified in a browser on production builds and in dev: zero CSP violations on the home page (scroll, theme toggle, project modal), login (a failed sign-in reaches Firebase and shows the normal error) and the admin pages; an external script, host and fetch are blocked. Against the same policy, markup-injection attacks are blocked while the trusted nonced script still runs: reflected `<script>`, `onerror=` handlers, `javascript:` links, a guessed nonce, `srcdoc` iframes. (`'strict-dynamic'` deliberately lets already-trusted code create scripts through DOM APIs, so a test that injects from the DevTools console/CDP will "succeed": that is not a hole, it is how the keyword works.) **If you add a third-party script, image host, font, embed or analytics, add its origin to the matching directive in `lib/csp.ts` (and give any inline script the nonce) or it will be blocked.** Changes to `next.config.ts` and `proxy.ts` need a dev-server restart.

## Rate limits (2026-10-06, live)
- **Rules (owner chose them):** contact form **3 messages per 10 minutes and 10 per day per visitor, 100 per day for the whole site**; admin login **5 failed attempts per 5 minutes per address**, then locked until the oldest failure is 5 minutes old. Refusals are `429` with a `Retry-After` header; the contact form says "Try again in about N min" (and keeps what was typed), the login form says "Try again in N minutes".
- **Limiter (`lib/limiter.ts`):** counts live in Firestore, **`rate_limits/<key>`** (a `hits` array of times plus `updatedAt`; Admin SDK only, not in `firestore.rules`, so clients are denied). Firestore, not memory, because Vercel runs many instances (the old in-memory limiter in `lib/analytics/rateLimit.ts` is still used by `/api/collect` and only knows its own instance). `consume(db, entries, now)` checks every rule of every entry and records one hit in one **transaction** (nothing is counted when refused, two simultaneous requests cannot both take the last place); `blockedFor` / `recordHit` / `clearHits` serve the login (only failures count); `waitFor` computes the wait. Keys: `limiterKey(purpose, ip, salt)` = `<purpose>_<salted sha256 of the address>` (no address stored; salt = `ANALYTICS_SALT`, else `ADMIN_UID`); `clientIp` reads `x-forwarded-for` then `x-real-ip`; no address means one shared "unknown" bucket. `pruneLimits` deletes counts untouched for 2 days, called (best effort) when the Analytics page opens.
- **Contact (`lib/contact.ts`, route is thin):** validation first (an invalid or honeypot request costs no count and no write), then `consume` over the visitor key (`VISITOR_RULES`) and `contact_site` (`SITE_RULES`), then the save. **If the limiter itself fails the message is still accepted** (a broken counter must not lose a real message).
- **Login (`lib/login.ts`, `app/api/login/route.ts`):** **the password is no longer checked in the browser.** The old flow (browser Firebase SDK `signInWithEmailAndPassword`, then `POST /api/auth/session` with the ID token) could not be limited because failed passwords never touched our server. Now `LoginForm` posts email + password to `/api/login`; `handleLogin` first asks `blockedFor` (a locked address gets 429 **without the password being tried**), then `signInWithPassword` (`lib/firebase-rest.ts`: Firebase Auth REST; wrong credentials = `INVALID_LOGIN_CREDENTIALS`/`INVALID_PASSWORD`/`EMAIL_NOT_FOUND`... all answer the same 401 "Invalid email or password."; Firebase's own `TOO_MANY_ATTEMPTS_TRY_LATER` counts as a failure; anything else, such as a bad key or a blocked referrer, is "unavailable" 502 and is **not** counted against the visitor), then `startAdminSession` (verifies the ID token and the owner UID, sets the cookie; a valid non-owner account gets 403 and counts as a failure). Failures are recorded, a success clears the address's failures. **Per address, never per account**, so nobody can lock the owner out by typing the owner's email. **If the limiter cannot be read, sign-in is refused (503): it fails closed.** `POST /api/auth/session` (the old token exchange) was **removed** to leave no second, unlimited way to start a session; `DELETE /api/auth/session` (sign out) stays.
- **Consequences / leftovers:** `LoginForm` no longer imports `@/lib/firebase`; only `SignOutButton` does (lazily, its `signOut` now only clears any old client state; could be dropped, then `lib/firebase.ts`, the `firebase` package and the CSP `connect-src` entries for `identitytoolkit`/`securetoken`/`www.googleapis.com` could go too: not done). The Firebase web API key must allow server calls (an HTTP-referrer-restricted key works because the server sends `Referer: <siteUrl>/`; an IP restriction would not).
- **Verified:** 58 new tests (limiter incl. window edges and transactions on a fake Firestore, contact rules, login rules, Firebase REST mapping, `LoginForm`, the 429 message in `ContactForm`); against the **real** Firebase on the dev server: 5 wrong passwords answered 401 (so the REST sign-in and the key work from the server), the 6th answered 429 with `Retry-After: 294`; a temporary key on the real Firestore allowed 3 and refused the 4th; the test documents were deleted. **Confirmed live by the owner on 2026-10-06:** signing in through the new route works on the deployed site (so the Firebase web API key accepts server calls), and the limits work. Deploy note: nothing to configure; `NEXT_PUBLIC_FIREBASE_API_KEY` is already set.

- **Animation is pure CSS** (`.term-line`, `.term-type`, `.term-cursor` in `globals.css`): each line appears at `--s` seconds, commands type with `steps(n, jump-start)` over `--d`; no JavaScript, starts on first paint, `aria-hidden` (decoration; the same facts are real text elsewhere), `prefers-reduced-motion` shows everything at once. **Gotcha:** the default `steps(n)` (jump-end) can stop one step short, because a long delay plus the duration leaves the animation at progress 0.9999999999999994 and the held value is the second to last step (the last letter of a command was cut off); `jump-start` avoids it. Measured: layout shift 0.0000, no horizontal overflow at 320/390/1200.
- Verified in headless Chrome on the public `/` (needs no login): dark and light, 1200/390/320 wide, plus reduced motion; unit tests for the generator in `lib/console.test.ts`. The admin editor's hero preview uses the same component. Not yet checked: PageSpeed with the console, and the look on a real phone.
